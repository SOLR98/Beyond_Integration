# Beyond Integration 模块化改造方案（按联动模组拆分）

> **⚠️ 已废弃（2026-11-22）**：本方案不再执行，仅作历史留档。
> 决策：取消现有方案；代码侧已落地的结构（0.8F `modules/`、0.8N/1.21.1N `feature/`）**保留不动**，后续以新方案为准。

> 数据基准：`D:\BI\worktrees\0.8-1.20.1-forge`（`dd3722a`，384 个 Java + 10 个 Kotlin）
> 方法：逐文件扫描 `import` 的第三方模组包名 + 内部类引用图，统计文件归属与模块间引用边
> 结论先行：**按模组切完全可行（384 个文件里只有 12 个真正跨模组），但不能先切——必须先反转 8 组"上帝文件"**，否则一定会切出 `kernel ↔ 模组` 的循环依赖。

---

## 1. 目标与非目标

**目标**

1. 每个联动模组一个模块，模块的失效边界 = 该模组不在时整块不加载。
2. 模块之间不允许横向 import（除显式 `bridge` 例外），由构建/脚本强制。
3. 新增一个联动模组 = 新建一个目录 + 在模块清单里加一行，不再改 6 个文件。
4. 为后续"0.8 线两个加载器共享同一份代码"铺路（模块化是共享的前提）。

**非目标（这一轮不做）**

- ❌ 不为每个模组出独立 jar。40 个联动模组 = 40 个下载，玩家不会接受；模块是**源码与依赖边界**，产物仍是 1 个 jar。
- ❌ 不动网络协议语义（只搬家，不改包结构）。
- ❌ 不合并 0.8 线的两个分支（那是下一阶段的事，见 §9）。

## 4. 第一步：反转 8 个上帝文件

### 4.1 模块接口（kernel/api）

只保留"依赖哪些模组"和"注册什么"，其余一律砍掉：

```java
public interface BiModule {
    /** 必须同时存在的模组 id；大多只有一个，哨戒是三个 */
    String[] requiredMods();
    /** 目标模组在时调用 */
    void register();
}
```

### 4.2 组装层（Bootstrap）

```java
public final class Bootstrap {
    // 唯一允许 import 全部模块的文件；列表顺序 = 注册顺序
    private static final List<Supplier<BiModule>> MODULES = List.of(
        TaczModule::new,
        GoetyModule::new,
        SuperbWarfareModule::new,
        TouhouLittleMaidModule::new,
        JeiModule::new,
        SentryModule::new,      // 依赖 tacz + create，排在 tacz 之后
        ThirstModule::new
    );

    public Bootstrap() {
        for (var s : MODULES) {
            BiModule m;
            try { m = s.get(); } catch (Throwable t) { continue; }        // 类缺失 = 模组没装
            if (!Mods.allLoaded(m.requiredMods())) continue;
            try { m.register(); } catch (Throwable t) { LOGGER.error("module failed", t); }
        }
    }
}
```

关键点：
- `Supplier` + `try/catch Throwable`，避免模块类在目标模组缺失时被解析。
- 组装层是**唯一**允许 `import modules.*` 的地方；CI 脚本对此做白名单校验（§8）。
- 原来 `BeyondIntegration.java` 里成片的 `if (isLoaded) ...` 注册块（438 行里的主体）全部变成模块内部的自洽逻辑。
- 不做拓扑排序：模块之间只允许依赖**类**（编译期），不允许依赖别的模块的**注册结果**；唯一需要顺序的是存档键，由 kernel 在模块之前统一注册。

### 4.3 网络包

```java
// kernel/net/Packets.java —— 不懂任何具体包，只有一张 id → 包 的表
public static void register(Class<? extends BiPacket> type, int id);

// modules/tacz/TaczModule.java
public void register() {
    Packets.register(TaczAmmoPushS2CPacket.class, 100);
    Packets.register(TaczCraftPacket.class, 101);
}
```

`PacketHandler` 从 286 行降到 ~60 行的框架，47 个包分散到各模块。**协议 ID 必须写成显式常量**，不能依赖注册顺序——模块拆开后顺序一定会变。

### 4.4 配置

`CommandConfig` 1289 行拆成：`kernel/config/CoreConfig`（通用项）+ 每个模块 `XxxConfig`（自己的项）。迁移期用同一个 TOML 文件、同一批 key 名，避免玩家配置丢失——**只改代码归属，不改 key**。

### 4.5 命令

`CommandLang`（1133 行）按模块拆成 `modules/tacz/lang/TaczLang.java` 等；命令树交给 `Commands.sub("insert", TaczInsertCommand::build)`，`BDNetworkCommands` 只留框架和根节点。

## 5. Mixin 的模块化

现在 72 条 Mixin 挤在一个 `beyond_integration.mixins.json`，由 270 行的 `MixinPlugin` 按 `targetClassName.startsWith(...)` 路由。改成：

```
modules/tacz/resources/beyond_integration.tacz.mixins.json
{
  "required": false,
  "package": "com.solr98.beyondintegration.modules.tacz.mixin",
  "plugin": "com.solr98.beyondintegration.modules.tacz.mixin.TaczGate",
  "mixins": ["AbstractGunItemMixin", ...],
  "client": [...]
}
```

每个模块一个 5 行的 Gate 子类（Mixin 的 config plugin 是「一个 config 一个类」，拿不到 config 名，所以不能用同一个类靠名字判断）：

```java
// kernel/mixin/ModGate.java —— 共享逻辑
public abstract class ModGate implements IMixinConfigPlugin {
    private static final Logger LOGGER = LogUtils.getLogger();
    protected abstract String requiredMod();          // "tacz" / "goety" / ...
    /** 子类覆写做版本/布局探测，默认放行 */
    protected boolean extraCheck(String target, String mixin) { return true; }

    @Override
    public boolean shouldApplyMixin(String target, String mixin) {
        var list = ModList.get();
        boolean on = list == null || list.isLoaded(requiredMod());
        if (!on) LOGGER.debug("[BI] skip mixin {} ({} absent)", mixin, requiredMod());
        return on && extraCheck(target, mixin);
    }
}

// modules/tacz/mixin/TaczGate.java —— 每个模块 5 行
public final class TaczGate extends ModGate {
    @Override protected String requiredMod() { return "tacz"; }
    @Override protected boolean extraCheck(String t, String m) { return isTaczApi115() || isBaseMixin(m); }
}
```

收益：
- 目标模组没装时，config 仍会加载，但**一条 Mixin 都不应用**，Mixin 类本身不会被解析 → 不会出现 `NoClassDefFoundError`；
- 删一个模块 = 删目录 + 删一行 `[[mixins]]`，不会留下孤儿条目；
- 顺手补上现在缺的**跳过日志**（4 份 MixinPlugin 全都没有 LOGGER）。

`mods.toml` / `neoforge.mods.toml` 里逐条声明：

```toml
[[mixins]]
config="beyond_integration.core.mixins.json"
[[mixins]]
config="beyond_integration.tacz.mixins.json"
...
```

> 注意：`mixins.json` 的 `package` 变了，Mixin 类的全限定名就变了，refmap 会重新生成——**这一步要与「重跑一次构建 + 进游戏验证」绑在一起做**，不能纯靠肉眼。

## 6. Gradle 落地：先用 sourceSet，别急着拆子工程

ForgeGradle 6 的多工程支持很痛（每个子工程都要 MC 依赖）。推荐三阶段：

**阶段 A（无构建改动）**：只按 §3 搬目录，加 §8 的 import 校验脚本。风险最低，先拿到结构收益。

**阶段 B（一个工程，多 sourceSet）**：

```groovy
sourceSets {
    kernel        { java.srcDir 'src/kernel/java' }
    modTacz       { java.srcDir 'src/modules/tacz/java' }
    modGoety      { java.srcDir 'src/modules/goety/java' }
    // ...
}
dependencies {
    modTaczImplementation sourceSets.kernel.output          // 只能看到 kernel
    modTaczImplementation fg.deobf("curse.maven:timeless-...")
}
// 产物仍是 1 个 jar：把各 sourceSet 的 output 合并进 jar
jar { from sourceSets.kernel.output, sourceSets.modTacz.output, ... }
```

sourceSet 的 `compileClasspath` 是逐 sourceSet 的，所以**Gradle 天然强制"模块只能看 kernel"**，比人肉 review 可靠。

> 坑：非 `main` 的 sourceSet **不会自动继承** `minecraft` 依赖。每个模块 sourceSet 都要显式补上加载器/原版类路径，例如
> `modTaczImplementation sourceSets.main.compileClasspath`（或把 `minecraft` 配置直接加到各 sourceSet）。
> 否则会出现"只有模块目录时找不到 `net.minecraft.*`"的假报错。

**阶段 C（真要独立产物时）**：再拆 Gradle 子工程 / 用 `jarJar` 嵌套。现阶段不需要。

## 8. 验收：让 CI 挡住回退

```powershell
# 规则：除 Bootstrap 外，任何文件不得 import 其它模块
$root = 'src/main/java/com/solr98/beyondintegration'
$bad = @()
Get-ChildItem "$root\modules" -Recurse -Include *.java | ForEach-Object {
  $mod = ($_.FullName -replace [regex]::Escape("$root\modules\"),'') -split '\\' | Select-Object -First 1
  $txt = Get-Content $_.FullName -Raw
  [regex]::Matches($txt,'import\s+com\.solr98\.beyondintegration\.modules\.([a-z0-9]+)\.') | ForEach-Object {
    if ($_.Groups[1].Value -ne $mod) { $bad += "$($_.Groups[1].Value) <- $($_.Name)" }
  }
}
Get-ChildItem "$root\kernel" -Recurse -Include *.java | ForEach-Object {
  if ((Get-Content $_.FullName -Raw) -match 'import\s+com\.solr98\.beyondintegration\.modules\.') { $bad += "kernel -> modules : $($_.Name)" }
}
if ($bad) { $bad | Write-Output; exit 1 }
```

三条硬规则：

1. `kernel/**` 不许 import `modules/**`；
2. `modules/A/**` 不许 import `modules/B/**`（白名单见 §2.2）；
3. 只有 `Bootstrap.java` 可以 import 全部模块。

## 9. 与"四分支"的关系（重要）

模块化只有在**同一份模块代码被两个加载器共用**时才真正省事。所以顺序应当是：

1. **在 0.8F 上做完模块化**（它功能最全、构建最干净）；
2. 把 `platform/` 与 `modules/*/net`、`modules/*/mixin` 做成双实现，其余模块代码**逐字共用**；
3. 再决定 0.8N 是"从 0.8F 重建"还是"保留分叉"。

如果反过来（两条分支各自模块化），你会得到 **2 份模块树 × 12 个模块 = 24 个需要同步的目录**，比现在的 4 份大文件更难维护。

## 10. 三个需要你先拍板的点

1. **配置是否随模块拆？** 拆了更干净，但老玩家的 `beyond_integration-common.toml` 里的 key 必须保号，否则设置全丢。建议：**保 key、只改归属**。
2. **`core-features/` 要不要也按"虚拟模组"处理？** 即 xp / charm / totem / terminal 这些不依赖第三方模组的功能，是继续叫 `feature/*`，还是也套进 `BiModule` 接口（这样它们也能单独开关）？建议套，统一模型。
3. **Mixin 边界**：`mixin/` 里有些 Mixin 同时服务两个模块（如 `VehicleAmmoMixin` 涉及 sw + BD）。这类是放进目标模组的 config，还是单独 `bridge` config？建议**跟着 target 类所属模组走**，bridge 只用于 target 不明确的情况。

## 11. 依赖策略：全部走公开坐标

模块化之后，"谁依赖什么"从一句话变成几十行声明。如果还混着本地源码构建和 `libs/*.jar`，这套结构立刻退化成"每个模块各有一堆本机专属路径"。所以定 5 条硬规则：

### 11.1 五条规则

1. **只声明公开坐标**：CurseMaven（`curse.maven:<slug>-<id>:<fileId>`）、Modrinth（`maven.modrinth:<project>:<versionId>`）或作者自己的 maven。禁止 `files("libs/xxx.jar")`、禁止 `Exec { commandLine "cmd","/c","gradlew.bat" }` 这类本地源码现编。
2. **Mixin 目标一律 `targets = "..."` + `@Pseudo`**，不要为了"能编译"就引整个模组 jar。这条已经在代码里被验证过（见证据表）。
3. **确实要 import 的目标类**，用公开坐标补齐，不用本地 jar。
4. **JDK 用 toolchain 声明**，禁止 `org.gradle.java.home=C:\...` 这种机器绑定。
5. **版本集中到 `gradle/libs.versions.toml`**，模块只写 `libs.tacz` 这样的别名，不散落 fileId。

### 11.2 证据：现有本地 jar 到底需不需要（逐文件核对）

| 分支 | 非标准依赖 | 实际编译需要吗 | 证据 | 处理 |
|---|---|---|---|---|
| `1.21.1-NEOFORGE` | `libs/emi-1.1.24+...jar` | **不需要** | 全仓唯一命中是 `MixinPlugin` 里的字符串 `dev.emi.emi.` | 删 |
| `1.21.1-NEOFORGE` | `libs/ponder-neoforge-...jar` | **不需要** | 全仓 0 处引用 | 删 |
| `1.21.1-NEOFORGE` | `libs/sentrymechanicalarm-...1.3.6.jar` | **不需要**（仅运行时） | 5 个 sentry Mixin 全是 `targets="euphy..."`，`import euphy` 计数 = 0 | 删编译依赖；开发环境放 `run/mods` |
| `1.20.1-forge` | `libs/jei-1.20.1-forge-15.56.0.205.jar` | **需要** | 2 个 `*NewMixin` 真 `import mezz.jei.gui.overlay.ingredients.*` | 换 `maven.modrinth:jei:9jqubC9n`（0.8F 已在用） |

| `0.8-1.20.1-forge` | 无（全 CF/Modrinth） | — | 51 条全部公开坐标 | 保持 |

### 11.4 版本锁定策略（模块化之后更重要）

- **构建**用**精确**版本（就是 CI 验证过的那个 fileId），不用区间。
- **`mods.toml` 的 versionRange** 只写到"确实验证过"的上界。现在 0.8F 声明 `beyonddimensions [0.8.3,)` 却按 0.8.9 编译，就是反例：玩家装 0.8.3 能过版本检查但会崩。
- **MixinPlugin 的探测能力**（TACZ 1.1.4/1.1.5+、taczaddon 1.1.8/1.2.0、JEI 新旧布局）决定 `versionRange` 能开多宽——**探不出来的版本区间就不要声明支持**。

### 11.5 对模块化的影响

- 每个模块的 `build` 片段 = 「kernel + platform + 自己的 1~3 个坐标」，一眼能看出这个模块依赖谁。
- 新增联动的成本从"改根 build.gradle + 改 PacketHandler + 改 MixinPlugin + 改 config"降到"加一行 catalog + 新建目录"。
- CI 可以按模块做"依赖最小化"检查：某模块的坐标集合如果包含别的模块的模组，说明切错了。
