# 预计结构（模块化目标树）

> **⚠️ 已废弃（2026-11-22）**：本目标树不再执行，仅作历史留档。
> 决策：取消现有方案；代码侧已落地的结构（0.8F `modules/`、0.8N/1.21.1N `feature/`）**保留不动**，后续以新方案为准。

> 基准：`0.8-1.20.1-forge` @ `dd3722a`（384 Java + 10 Kotlin）
> 本文是"改完长什么样"的定稿：目录树、依赖矩阵、每个模块装哪些文件、跨模组文件落点、分几期落地。
> 配套：[模块化改造方案-按联动模组拆分.md](模块化改造方案-按联动模组拆分.md)、[附属归类表.md](附属归类表.md)

**已定的六条**（后续讨论请以这六条为前提）：

1. **两层切法**：`features/<域>` 放不依赖第三方模组的抽象（键/数据/迁移），`modules/<模组>` 放真正调模组 API 的那一半。
2. **附属内置**：完全依赖父模组的附属（taczaddon）放 `modules/tacz/enhance/taczaddon/`，不单独成模块；父模组没有模块的附属（sentry、rs-integration）才自成模块。
3. **注册只判 `isLoaded`**：`BiModule` 只有 `requiredMods()` + `register()`，不做拓扑排序，顺序靠 `Bootstrap` 列表。
4. **通用方法先抽**：重复 ≥2 模块且无模组类型的进 `kernel/util`，有 BD 类型的进 `features/common`。
5. **产物仍是 1 个 jar**：模块是源码/依赖边界，不是分发单位。
6. **先做 0.8F 一条分支**：0.8N 与它相似度 27%，同时改等于双倍返工。

## 1. 先定一条原则：两层切法

一开始想的是"`feature/soul` → `modules/goety`"，但实测数据不支持——**每个 feature 域里约有一半根本不 import 第三方模组**：

| 功能域 | 总数 | 不依赖联动模组 | 依赖联动模组 |
|---|---|---|---|
| `feature/soul` | 16 | **10**（灵魂键、来源抽象、迁移） | 6（goety 实现） |
| `feature/mana` | 11 | **9**（魔力键、网络源、HUD） | 2（irons） |
| `feature/ammo` | 20 | **10**（网络弹药容器、索引、迁移） | 8 + 2 桥 |
| `feature/enchant` | 11 | **8**（附魔台、合并、分书） | 3（apoth） |
| `feature/feeder` | 9 | **5**（四档水纯度） | 4（thirst） |
| `feature/terminal` | 6 | **5**（绑定 Hub、目标接口） | 1（sw 载具） |
| `feature/maidpower` | 5 | **4**（P 点键与访问） | 1（tlm） |

所以正确切法是两层，而不是整体搬家：

```
features/<域>   抽象层：数据结构、键、接口、迁移、算法   —— 只依赖 BD
modules/<模组>  实现层：真正调用第三方模组 API 的那一半 —— 依赖 features/<域>
```

好处：删掉一个联动模组，抽象层和已存存档数据还在（键仍能反序列化），只是实现没了。这正好符合现在 `SoulKeyRegistration` 的"键必须先注册"约束。

### 2.1 依赖矩阵（只允许向下）

| 从 ＼ 可依赖 | kernel | platform | features | modules | bridge | ui | 第三方坐标 |
|---|---|---|---|---|---|---|---|
| `Bootstrap` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| `ui` | ✅ | ✅ | ✅ | 仅 client 接口 | — | — | Compixel、Kotlin |
| `modules/X` | ✅ | ✅ | ✅ | 仅上游（sentry → tacz） | 仅 bridge | — | X 自己的 |
| `features/X` | ✅ | — | 仅 `features/common` | ❌ | ❌ | ❌ | ❌ |
| `platform` | — | — | ❌ | ❌ | ❌ | ❌ | BD、加载器 |
| `kernel` | — | ✅ | ❌ | ❌ | ❌ | ❌ | BD、原版 |

三条硬规则：`kernel` 不碰 `features/modules`；`features` 不碰 `modules`；模块之间只有一条合法边 = 编译期上游（且方向单一）。

### 2.2 现状 → 目标 的落位

| 现状 | 去向 |
|---|---|
| `BeyondIntegration.java` | `Bootstrap.java` |
| `network/*Packet` | `modules/<模组>/net`（核心包 → `kernel/net`） |
| `mixin/*Mixin` | 目标模组所属的 `modules/<模组>/mixin`；跨模块的进 `bridge` |
| `command/*` | 框架 → `kernel/command`；子命令 → `modules/<模组>/command` |
| `handler/*` | 通用 → `kernel/util`；BD 相关 → `features/common`；模块专属 → `modules/<x>` |
| `client/*` | 通用 HUD/GUI → `ui`；模块专属 → `modules/<x>/client` |
| `core/*` | `kernel`（`sync/`、`log/`、`util/` 原样保留） |
| `init/*` | 注册项下放各模块，只剩注册器在 `kernel/api` |
| `feature/<域>` | 抽象一半 → `features/<域>`；模组实现一半 → `modules/<模组>` |
| `compat/*` | 归属模组的 `modules/<模组>` |
| `jei/`、`jade/`、`maid/`、`integration/ae2lt/` | 各自的 `modules/<id>` |

> 落位清单按「文件直接 import 了哪个模组」机械得出，按领域归位时约 5 个文件会跨类移动（`PacketHandler` → `kernel/net`、`Tacz*` 包 → `tacz`），模块数字上下浮动 1~3 个，不影响划分。

## 4. 通用能力要先抽掉，否则每个模块各长一份

模块切完最容易出现的结果是：12 个模块各自写一遍 `ItemStack` 编码、玩家守卫、模组判断。所以要先把"跨模块通用的那部分"提出来，模块才有东西可依赖。

### 4.1 放哪：判断三问

1. 参数/返回值里有 **BD 类型**？→ `features/common`（BD 抽象层）
2. 有**第三方模组类型**？→ 留在 `modules/<模组>`
3. 被 **≥2 个模块**用，且上面两条都不成立？→ 提升到 `kernel/util`

只被一个模块用、又不含第三方类型的，留在该模块 `internal/`，**不要提前抽象**。

### 4.2 实测重复（0.8F，4 行窗口扫描 + 正则计数）

| 重复模式 | 次数 | 涉及文件 | 现状 | 目标落点 |
|---|---|---|---|---|
| `FriendlyByteBuf` 读写 ItemStack | 172 | 54 | 每个 packet 手写 encode/decode | `kernel/net/BufCodec` |
| `Component.literal/translatable` | 514 | 63 | 到处构造 + `withStyle` | `kernel/util/Text` |
| `catch (Throwable)` 吞异常 | 80 | 42 | 每处各写一段 | `kernel/util/Safe` |
| `ModList.get().isLoaded(...)` | 54 | 29 | 散落各处 | `kernel/util/Mods` |
| `getOrCreateTag()/getTag()` | 47 | 25 | F 线没有 `ItemNbt` | `kernel/util/ItemNbt`（N 线已有，上移） |
| 命令前置守卫 | 8 个文件同一段 | command | 复制粘贴 | `kernel/command/Guards` |
| 网络包"取网"守卫 | 7 个文件同一段 | network | 复制粘贴 | `kernel/net/PacketContext` |
| StackKey 样板（`getTypeID/getEmpty`） | 5 个类同构 | features | 各自实现 | `features/common/NetKey` 基类 |

命令里最典型的复制粘贴（8 个文件一字不差）：

```java

if (executor == null) {
    source.sendFailure(OutputFormatter.createError("error.player_required"));

```

网络包里的另一处（7 个文件一字不差）：

```java

if (player == null) return;
DimensionsNet net = NetMenuResolver.resolve(player);

```

另外 JEI 的 4 个 Mixin（新旧布局成对）共享同一段 tooltip 逻辑，只差 target 类型，属于"同一实现的两个变体"，应该收成一个模板方法而不是四份。

### 4.4 抽取顺序（跟着模块走，不要一次全抽）

| 阶段 | 抽什么 | 理由 |
|---|---|---|
| 与 P1 同批 | `BufCodec`、`Guards`、`PacketContext` | P1 的 5 个模块（tacz/goety/sw/tlm/jei）大量依赖这三样，不先抽它们会各自复制 |
| P2 | `Text`、`Safe`、`Mods`、`Numbers` | 使用面广但风险低，可以后置 |
| 最后 | `NetKey` 基类、`NetAccess` | 动到 BD 存档键体系，`getTypeID()` 必须一字不变，风险最高 |

收益估计：约 600–800 行样板消失；新增一个 packet 从 ~30 行降到 ~10 行；新增一个网络命令从 ~15 行前置代码降到 2 行。

## 6. 三个容易踩的结构性坑

### 6.1 包名一变，refmap 全废

Mixin 类换包 → `mixins.json` 的 `package` 变 → refmap 重新生成。**这一刀只能挨一次**：建议在 P1 就把所有模块的包名定死（`...modules.tacz.mixin`），后面只搬不改名。分几次改包名会反复触发全量 refmap 重编。

### 6.2 协议 ID 不能跟着目录走

现在 47 个包靠注册顺序拿 ID（`SimpleChannel` 自增）。拆模块后注册顺序会变——**必须改成显式 ID**（`registerMessage(id, ...)`），否则老存档/联机握手会错位。这是模块化里唯一"必须改行为"的地方。

### 6.3 Kotlin/Compose 页只有 0.8 线有

`ui/` 里的 10 个 `.kt` 依赖 Compixel + Compose 编译器插件。0.8N 分支也有，所以 `ui` 模块在两条分支上是同构的；但 0.7 线没有 `ui/page`，结构会少一块——这也是**先做 0.8 线**的另一个理由。

## 7. Gradle 侧的结构

```groovy
sourceSets {
    kernel      { java.srcDir 'src/kernel/java' }
    platform    { java.srcDir 'src/platform/java' }
    features    { java.srcDir 'src/features/java' }
    modTacz     { java.srcDir 'src/modules/tacz/java' }
    // ... 12 个
    ui          { java.srcDir 'src/ui/java'; java.srcDir 'src/ui/kotlin' }
}
```

依赖声明（`libs.versions.toml` 别名见方案 §11.3）：

```groovy
dependencies {
    modTaczImplementation sourceSets.kernel.output
    modTaczImplementation sourceSets.features.output
    modTaczImplementation libs.tacz
    modTaczImplementation libs.taczaddon
```

产物仍是 1 个 jar，`jar { from sourceSets.kernel.output, sourceSets.features.output, ... }` 合并。

> MC/加载器类路径不会自动继承到非 main sourceSet，每个模块要显式补 `sourceSets.main.compileClasspath`。
> 模块数会继续涨（目标 30），这 12 段 sourceSet 建议直接上 §9.2 的自动发现，**别手工维护**。

## 9. 为"以后还会加更多联动"设计：目录即模块

现在的 6 步里有 3 步要碰公共文件（catalog、`Bootstrap`、build sourceSet）。12 个模块还能忍，涨到 30 个就是 merge 冲突热点。目标改成：**新增一个联动 = 只加一个目录**。

### 9.1 模块目录契约

```
src/modules/<id>/
├─ module.gradle                    # 全模块唯一声明依赖的地方（引 catalog 别名）
├─ java/com/solr98/beyondintegration/modules/<id>/
│  ├─ <Id>Module.java               # implements BiModule
│  ├─ feature/                      # 业务（服务端/公共）
│  ├─ client/                       # 客户端
│  ├─ net/                          # 网络包
│  └─ mixin/                        # 注入
└─ resources/
   ├─ beyond_integration.<id>.mixins.json      # 可选
   └─ assets/beyond_integration/lang/<id>_*.json  # 可选，模块自带文案
```

### 9.2 两处自动化

| 现在手写的 | 改成 |
|---|---|
| build.gradle 里 30 行 `modXxxImplementation` | 扫 `src/modules/*` 动态建 sourceSet |
| `mods.toml` 里逐条 `[[mixins]]` | `processResources` 扫 `beyond_integration.*.mixins.json` 自动生成 |

模块清单**不自动生成**——`Bootstrap` 里手写 20~30 行 `List.of(...)`，一眼能看出加载顺序，比生成的索引更好读。

```groovy
// 自动发现模块：新增目录即新增模块
file('src/modules').listFiles().findAll { it.isDirectory() }.each { dir ->
    def id = dir.name.replace('-', '_')
    def ss = sourceSets.create("mod_${id}") { java.srcDir "${dir}/java" }
    ss.compileClasspath += sourceSets.kernel.output
    ss.compileClasspath += sourceSets.features.output
    ss.compileClasspath += sourceSets.main.compileClasspath     // MC/加载器
    apply from: "${dir}/module.gradle"        // 模块自带依赖，用 mod_<id>Implementation 声明
}
```

```groovy
// src/modules/tacz/module.gradle —— 模块唯一的依赖声明处
dependencies {
    mod_taczImplementation libs.tacz
    mod_taczImplementation libs.taczaddon
}
```

### 9.3 模块契约：只判断"装了没装"

注册面收缩到最小，一个模块只回答两件事：**依赖哪些模组**、**注册什么**。

```java
public interface BiModule {
    /** 必须同时存在的模组 id；大多只有一个，哨戒是三个 */
    String[] requiredMods();
    /** 目标模组在时调用；内部自己决定注册什么 */
    void register();
}
```

```java
// Bootstrap —— 全仓唯一 import 所有模块的文件
private static final List<Supplier<BiModule>> MODULES = List.of(
    TaczModule::new,
    GoetyModule::new,
    SuperbWarfareModule::new,
    TouhouLittleMaidModule::new,
    JeiModule::new,
    SentryModule::new,          // 依赖 tacz + create，排在 tacz 之后即可
    ThirstModule::new
    // ...
);

public Bootstrap() {
    for (var s : MODULES) {
        BiModule m;
        try { m = s.get(); } catch (Throwable t) { continue; }       // 类缺失 = 模组没装
        if (!Mods.allLoaded(m.requiredMods())) continue;
        try { m.register(); } catch (Throwable t) { LOGGER.error("module failed", t); }
    }
}
```

实现只有几行：

```java
public final class SentryModule implements BiModule {
    public String[] requiredMods() { return new String[]{"sentrymechanicalarm", "tacz", "create"}; }
    public void register() {
        Packets.register(SentryPacket.class, 210);
        ClientHooks.add(SentryOverlay::render);
    }
}
```

**为什么不需要拓扑排序**：模块之间只允许"编译期依赖类"，不允许依赖"另一个模块的注册结果"。唯一的顺序敏感点是**存档键必须先注册**——由 `kernel` 在任何模块之前统一注册 `features/common` 的键，顺序问题从结构上消失。剩下极少数真需要顺序的（如 `sentry` 排在 `tacz` 之后），靠列表顺序 + 一行注释即可。

**放弃了什么**：`side()` → 模块内部自己判断 `Dist`；`verifiedVersionRange()` → `mods.toml` 手写；`ModuleIndex` 自动生成 → 手写 20 行列表，可读性反而更好。这些都不影响隔离性。

### 9.3.1 注册用静态注册器，不传上下文

```java
// kernel/net/Packets.java
public static void register(Class<? extends BiPacket> type, int id);

// kernel/command/Commands.java
public static void sub(String root, LiteralArgumentBuilder<CommandSourceStack> node);

// kernel/config/Configs.java
public static void section(String moduleId, Consumer<ConfigBuilder> b);

// kernel/client/ClientHooks.java
public static void add(Runnable hook);          // 内部按 Dist 分流
```

模块少一个参数，kernel 少一个 `ModuleContext` 类。

> `sentry-arm` 同时依赖 `create` 与 `tacz`，所以 `requiredMods()` 返回三个 id；它不能 `inline` 到 tacz，因为父是 Create、只是恰好也用 TACZ。

### 9.4 新增模块 checklist（写进 CONTRIBUTING）

1. 建目录 + `module.gradle`
2. `<Id>Module.java`：`requiredMods()` + `register()`（多个上游要列全）
3. 业务 `feature/`、客户端 `client/`、包 `net/`、注入 `mixin/`
4. 新增 target 就给 mixin config
5. Gate 子类（5 行）
6. 文案：`lang/<id>_zh_cn.json` + `en_us.json`，key 前缀 `beyond_integration.<id>.`
7. 配置：`<Id>Config`，key 前缀同上
8. 命令：`Commands.sub(...)`，**不许碰 `BDNetworkCommands`**
9. 数据键：在 `features/common` 注册，**模块不许私建键**
10. 降级：目标模组缺失时，`features/<域>` 的键与存档数据仍可读写
11. 文档：`docs/modules/<id>.md`
12. 冒烟两条：只装 BD + 该模组启动；不装该模组启动

### 9.5 规模预期

| 模块数 | sourceSet | `Bootstrap` 列表 | 新增一个的成本 |
|---|---|---|---|
| 现在 12 | 12（自动发现） | 12 行 | 1 个目录 + 1 行 |
| 目标 30 | 30（自动发现） | 30 行 | 1 个目录 + 1 行 |

### 9.6 反模式

| ❌ 不要 | 理由 |
|---|---|
| 一个模块塞两个**独立**模组（jei + jade 合并） | 失效边界不同，一个装了另一个没装时会互相拖累。附属（`inline`）不受此限——它本来就没有独立边界 |
| 模块之间直接 import | 除编译期依赖的上游模块（如 sentry → tacz）；方向单一，不许回指 |
| 通用件留在模块里 | 下次复制粘贴；应进 `kernel/util` 或 `features/common` |
| 模块自己开新存档键 | 卸载模块后存档读不出，破坏降级 |
| 模块自带网络 ID 段 | 47 个包已经要显式 ID，再分段必然冲突 |

## 10. 附属模组（addon）怎么放

联动模组里有一半是"附属"：`taczaddon → tacz`、`goety-revelation → goety`、`rs-integration → refined storage`、`sentry-arm → create`、`apothic-attributes → apotheosis`、`tacz-unidict → tacz`、`ae2lt → AE2`。

但**"完全依赖"恰恰是它不该单独成模块的理由**：`taczaddon` 没有 `tacz` 就跑不起来，所以"taczaddon 装没装"只是 `tacz` 模块内部的一个开关，撑不起一个独立的失效边界。相反，`rs-integration` 的父模组 RS 在本项目里没有模块，它才必须自成模块。

> **这一节只是默认建议，不是规则。**实际归类由人工维护的 `modules.toml`（模板见 [附属归类表.md](附属归类表.md)）拍板，构建以表为准；表里没填的坐标会让构建直接报"未归类"。

### 10.1 判据：先看父模组有没有模块，再看依赖是否完全

| 情况 | 例子 | 处理 |
|---|---|---|
| 父模组有模块 + 附属完全依赖它 | taczaddon → tacz、tacz-unidict → tacz、goety-revelation → goety | **内置**到父模块的 `enhance/<addon>/`，不单独成模块 |
| 父模组没有模块（只作为前置/库） | rs-integration → RS、sentry-arm → Create | **自成模块**，否则无处安放 |
| 前置库：纯 API/运行时，不提供玩法 | thunderbolt-core、placebo、libipn、zeta、geckolib、kotlin-for-forge、compixel | 只进 `libs.versions.toml`，**不进 modules** |
| 同作者兄弟：可独立安装的平行内容 | mekanism tools/generators、thirst-was-reclaimed | 各自独立模块，或都不建 |

一句话：**附属只有在"父模组没被模块化"时才需要自己的模块；否则内置。**

### 10.2 内置形态：`enhance/` 子包

```
modules/tacz/
├─ TaczModule.java
├─ feature/  client/  net/  mixin/          ← TACZ 本体
└─ enhance/
   └─ taczaddon/
      ├─ TaczaddonEnhancer.java             ← 入口，由 TaczModule 在 isLoaded 时调用
      ├─ mixin/TaczaddonCraftBridgeMixin.java      # 1.1.8
      ├─ mixin/TaczaddonCraftBridgeMixinNew.java   # 1.2.0
      ├─ mixin/TaczaddonGate.java
      └─ resources/beyond_integration.taczaddon.mixins.json
```

`TaczModule` 里只多一行：

```java
if (Mods.loaded("taczaddon")) ctx.enhance(TaczaddonEnhancer::register);
```

`enhance/*` 仍然是**内嵌叶子包**：父模块的 `feature/client/net` 不许 import 它；mixin 配置仍独立（config + Gate），addon 缺席时这一份 config 一条都不 apply。

### 10.3 三条铁律（内置同样适用）

1. **父模块的业务代码不许 import `enhance.*`**。要知道增强在不在，只允许 `Mods.loaded("taczaddon")` 这种字符串判断。
2. **父模块定接口，enhance 实现**。例如 `features/crafting/CraftBridge`（空实现 = 不支持网络合成），enhance 里提供真实实现并在注册时替换。缺 addon 时退化为"不支持"，而不是崩溃。
3. **共享的数据键放 `features/common`**，两侧都不许私建。addon 卸载后键仍要能反序列化。

### 10.4 版本适配关在 enhance 里，不外溢

taczaddon 1.1.8 → 1.2.0 是大重构（删了 `ContainerItemSource`、`GunSmithCompatibilityService`，`GunSmithCraftBridgeState` 换包并去掉 `requestCraft`）。`TaczaddonGate` 用 `hasMethod("requestCraft")` / `hasMethod("request")` 二选一，**TACZ 本体代码一行都不用改**。

这就是内置的代价与收益：模块数不涨，但 addon 的多版本适配必须在 `enhance/` 内部自己消化。

### 10.5 版本声明是二维的

`mods.toml` 的 `versionRange` 一次只能写一个模组，addon 需要两条（父 + 子）：

```toml
[[dependencies.beyond_integration]]
modId = "tacz"
versionRange = "[1.1.5,1.3)"

[[dependencies.beyond_integration]]
modId = "taczaddon"
versionRange = "[1.2.0,1.3)"
```

文档里同步维护一张二维表（现在 `0.8.x-TACZ与哨戒兼容记录.md` 里手写的就是这张表）——**这里是唯一需要人工保持同步的地方**，不再做代码里生成。

### 10.6 什么时候才把 `enhance/` 提成独立模块

满足**任一条**：

1. 文件数超过 ~30，或需要单独发布/单独 jar；
2. 附属开始**脱离父模组版本节奏**（例如将来 taczaddon 支持 TACZ 之外的枪械库）；
3. 同一个增强要服务**两个父模块**——这种情况定义为 `bridge/`，不是模块。

`taczaddon` 目前三条都不满足（5 个 Mixin + 1 个服务类），所以内置在 `mod-tacz/enhance/taczaddon/`。

### 10.7 规模影响

内置附属**不增加模块数**：30 个联动 + 6~10 个附属，模块仍是 30 上下，只是目录里多一层 `enhance/`。这就是"完全依赖"带来的简化——附属不是边界，父模组才是。

## 11. 还需要你确认的两处

1. `features/` 与 `modules/` 谁依赖谁：本草案是 **modules → features**（实现层依赖抽象层）。反过来（features 引用 modules 的具体实现）会重新引入环，不建议。
2. `ui/` 是独立模块还是并进 `kernel/client`：本草案独立，因为它同时依赖 kernel 和各模块的 client 接口，并进 kernel 会破坏"kernel 零依赖"。
