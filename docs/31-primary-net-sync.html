31 · 主网络同步统一机制

配置驱动选择性推送 · 客户端全量镜像接口 · 条件式取数 · 异常重同步 · 仅 1.20.1-FORGE

一、目标

把「主网络库存 / 状态」的同步从 JEI 专属升级为通用同步设施：

  • 服务端按配置 scope 选择性推送主网络数据；
  • 客户端维护一份镜像（接口化，可供任意功能读取）；
  • 各业务条件式取数：范围覆盖则读镜像，否则回退各自独立通道；
  • 异常时客户端请求重新同步，自动恢复一致。
一句话配置在服务端决定“推什么”，包内 typeMask 声明“推了什么”，业务据此条件取数；默认关闭时零成本、行为不变。

二、设计原则与边界

原则

  • 配置为权威来源在服务端；客户端以「实际收到的类型位」为准，不重复读本地配置做可用性判断，避免同步竞态。
  • 默认 primary_net_sync=false + scope=ITEMS ⇒ 零成本、行为不变。
  • 服务端业务永不依赖客户端镜像（S2C 单向）。
  • 客户端各业务缓存仍独立；镜像只作共享的只读派生源。
  • 客户端镜像 extends AbstractUnorderedStackHandler ⇒ 天然是 BD IStackHandler，复用全部现有只读扫描逻辑。
  • 所有发送/刷新延迟到 tick 合并；回调（BD delta）只置脏，不发包、不扫全表。

边界

  • Goety SE 永不共享（不在网络）。
  • 服务端扣弹 / 取魂等判定继续直读 UnifiedStorage，不做条件式。
  • 玩家背包库存客户端本地即有，不参与同步。

四、端到端数据流

配置(enabled + scope) ──推送──▶ SyncConfigClient(客户端运行时配置)
                                      │
服务端 PrimaryNetSyncManager ──按 scope 过滤──▶ PrimaryNetSyncPacket(typeMask)
                                      │
客户端 PrimaryNetClientStorage.apply(...) ──▶ 镜像(availableTypes = typeMask)
                                      │
业务 ── SharedNetData.available(type) ? 读镜像 : 回退独立通道
                                      ▲
                        异常 ──▶ SyncResyncRequestPacket(C2S) ──▶ 服务端重建基线全量重推

阶段 1 · 配置推送链路

内容

服务端把运行时配置显式推给客户端，作为后续类型位 / 条件取数的权威依据。

实现方法

  • network/SyncConfigSyncPacket.java S2C：boolean enabled + int scopeOrdinal
  • client/SyncConfigClient.java 客户端运行时配置缓存：isActive() / scope() / reset()
  • handler/NetworkSyncConfigPusher.java 登录 / 配置重载时推送（@Mod.EventBusSubscriber FORGE）
public final class SyncConfigClient {
    private static volatile boolean enabled = false;
    private static volatile PrimaryNetSyncScope scope = PrimaryNetSyncScope.ITEMS;
    public static void set(boolean e, PrimaryNetSyncScope s) { enabled = e; scope = s; }
    public static boolean isActive() { return enabled; }
    public static PrimaryNetSyncScope scope() { return scope; }
    public static void reset() { enabled = false; scope = PrimaryNetSyncScope.ITEMS; }
}

要求

  • 与是否安装 JEI 无关（无条件注册 / 推送）。
  • 配置包须早于首个 PrimaryNetSyncPacket 发出（登录同 tick 先发配置）。
  • 断线时 SyncConfigClient.reset()；PacketHandler.register() 注册该包。
  • 包极小（2 字段），无性能负担。

阶段 2 · 服务端按 scope 选择性推送

内容

PrimaryNetSyncManager 按 scope 过滤；包携带 typeMask；配置变更重建基线重推。

实现方法

  • PrimaryNetSyncPacket 增加 int typeMask（1 << NetDataType.ordinal()），clear 包携带 typeMask=0。
  • flush 过滤：
for (KeyAmount ka : storage.getStorage()) {
    if (ka.isEmpty() || !scope.covers(NetDataType.of(ka.key()))) continue;
    now.merge(ka.key(), ka.amount(), Long::sum);
}
  • 配置变更：配置重载回调中对 SESSIONS 全部 dirtyFull=true、lastSent.clear()，按新 scope 全量重推，并推送新配置包。

要求

  • flush 仍遵循“仅脏 / 有 pending 才发”。
  • typeMask 必须与实际打包内容一致（否则客户端落库错位）。
  • 空闲仍零发包，不因 scope 改变新增每 tick 开销。

阶段 3 · 客户端镜像接口与实现

3a 接口与枚举

public interface ClientNetworkMirror {          // 只读：业务消费端
    boolean hasNetwork();
    int netId();
    boolean supports(NetDataType type);         // = typeMask 含该类型
    int version();
    long getCount(IStackKey<?> key);
    java.util.OptionalLong getAmount(NetDataType numericType);  // ENERGY / SOUL
    Map<String, Long> getExtAmmo();             // EXT_AMMO
    String getNetworkName();
    boolean getFlag(NetFlag flag);
    void clear();
}

public interface ClientMirrorSink {             // 写入：网络包 handler
    void apply(boolean clear, boolean hasNetwork, int netId, int typeMask,
               Map<IStackKey<?>, Long> counts,
               Map<String, Long> extAmmo, String name, long flagsBits);
    void clearAll();
}

3b 实现（兼容现有静态调用）

public final class PrimaryNetClientStorage
        extends AbstractUnorderedStackHandler          // = IStackHandler
        implements ClientNetworkMirror, ClientMirrorSink {
    public static final PrimaryNetClientStorage INSTANCE = new PrimaryNetClientStorage();
    private int availableTypes = 0;   // typeMask
    private int netId = -1; private boolean hasNetwork = false; private int version = 0;

    private PrimaryNetClientStorage() {
        super(ZeroPolicy.REMOVE_ON_ZERO, UiTimestampPolicy.NONE);
    }
    @Override public void onChange() { /* no-op：镜像不触发 BD 事件回环 */ }

    // 旧静态方法委托 INSTANCE（JEI 助手零改动）
    public static long getCount(IStackKey<?> k) { return INSTANCE.getCount(k); }
    public static boolean hasNetwork() { return INSTANCE.hasNetwork(); }
}

3c apply 语义

  • 落库范围内类型；清除 availableTypes 中被移除的类型数据（scope 降级）；version++。

要求

  • 继承 AbstractUnorderedStackHandler ⇒ 具备 getStackByKey / getBucket / getStorage，直接兼容 scanNetworkItems、countSubstitutable(IStackHandler, …)。
  • onChange() 必须 no-op（避免镜像内部写触发事件 / 脏标记）。
  • 旧静态 API 签名与行为保持不变；仅主线程访问。

阶段 4 · 条件式取数 API

实现方法

public final class SharedNetData {
    private static ClientNetworkMirror mirror() { return PrimaryNetClientStorage.INSTANCE; }
    public static boolean available(NetDataType t) {
        return mirror().hasNetwork() && mirror().supports(t);
    }
    public static OptionalLong soul(int netId)   { return available(SOUL)   ? mirror().getAmount(SOUL)   : OptionalLong.empty(); }
    public static OptionalLong energy(int netId) { return available(ENERGY) ? mirror().getAmount(ENERGY) : OptionalLong.empty(); }
    public static Optional<Map<String,Long>> extAmmo() { return available(EXT_AMMO) ? Optional.of(mirror().getExtAmmo()) : Optional.empty(); }
    public static long itemCount(IStackKey<?> key) { return mirror().getCount(key); }
}

要求

  • available 以服务端实际推送的类型位为准（不重新读本地配置）。
  • 只读、无副作用。

阶段 5b · TACZ 合成库存（方案 A）

  • 重构 RequestNetworkItemsPacket.scanNetworkItems(DimensionsNet) → scanNetworkItems(IStackHandler storage, Map<String,List<TaczIngredient>> index)。 服务端传 net.getUnifiedStorage()，客户端传 PrimaryNetClientStorage.INSTANCE。
  • buildIndex 改为接受 RecipeManager（客户端本地配方，已同步）。
  • 桶装折算直接用现成 BucketFluidHelper.countSubstitutable(IStackHandler, …)。
  • 背包材料仍取本地 player.getInventory()（不参与同步）。
  • 条件：available(ITEM) 时客户端重算；否则回退现有 RequestNetworkItemsPacket 请求通道。
关键scanNetworkItems 逻辑单份，两端同一份；NBT partial / 桶装折算语义与服务端一致。TACZ 配方由 datapack 同步，客户端 RecipeManager 已含 GunSmithTableRecipe。

配方索引：预构建缓存（参考 JEI RecipeMap）

JEI 的做法：RecipeManagerInternal 构造 RecipeMap，在配方加载后遍历配方，对每个原料取 getUniqueId(ingredient, UidContext.Recipe)，建立「原料 uid → 配方类型」反向索引并常驻内存，配方重载时重建，查询 O(1)。

BI 当前 TACZ_INDEX 为「请求时惰性构建 + 校验重建」，首个请求会承担构建开销。改为预构建缓存：

  • feature/ammo/tacz/TaczRecipeIndex.java build(RecipeManager) / isReady() / 查询；索引结构参考 RecipeMap
  • 客户端：监听 RecipesUpdatedEvent，配方就绪后一次性构建并缓存。
  • 服务端：监听 OnDatapackSyncEvent（数据包 / 配方同步后）构建并缓存。
  • scanNetworkItems / buildIndex 直接读缓存；配方重载时由事件重建；未就绪时回退（惰性构建或返回空）。

要求

  • 逐业务独立可回滚；未覆盖类型必须走原通道且行为与现状一致。
  • 不引入新的每 tick 轮询（沿用事件 / 订阅 + tick 合并）。

阶段 6 · 异常恢复（重新同步）

异常分类

类别判定处理
A. 协议 / 时序typeMask 含 SyncConfigClient.scope() 之外的位；未知类型位；解码异常resync + 配置重推
B. 状态不一致总开关开启但镜像长时间 hasNetwork()==false；业务查询发现应有却缺resync
C. 版本停滞镜像 version 长时间不变但预期应有变化谨慎（易误判），仅超长阈值触发

协议：C2S 请求包

public final class SyncResyncRequestPacket {
    private final int reason;  // 0=unknown,1=config_mismatch,2=state_missing
    public static void handle(msg, ctx) {
        ServerPlayer p = ctx.get().getSender();
        if (p != null) PrimaryNetSyncManager.requestResync(p, msg.reason);
    }
}

服务端处理（幂等 + 双向限流）

private static final Map<UUID, Long> LAST_RESYNC = new HashMap<>();
private static final long RESYNC_COOLDOWN = 100; // tick

public static void requestResync(ServerPlayer player, int reason) {
    long now = player.getServer().getTickCount();
    Long last = LAST_RESYNC.get(player.getUUID());
    if (last != null && now - last < RESYNC_COOLDOWN) return;   // 服务端防刷
    LAST_RESYNC.put(player.getUUID(), now);

    Session s = SESSIONS.get(player.getUUID());
    if (s != null) {                       // 已绑定：下一 tick 全量重推
        s.dirtyFull = true; s.pending.clear(); s.lastSent.clear();
    } else {                               // 未绑定：下 tick 重新 bind
        PENDING.remove(player.getUUID());
    }
    NetworkSyncConfigPusher.push(player);  // 顺带重推配置，保证 scope 一致
}

客户端触发（本地冷却）

public final class SyncResyncClient {
    private static long lastRequestTick = Long.MIN_VALUE;
    private static final long COOLDOWN = 100; // tick
    public static void request(int reason) {
        long now = clientTick();
        if (now - lastRequestTick < COOLDOWN) return;
        lastRequestTick = now;
        PacketHandler.sendToServer(new SyncResyncRequestPacket(reason));
    }
}
  • PrimaryNetClientStorage.apply：typeMask 出现超出 SyncConfigClient.scope() 的位 → request(CONFIG_MISMATCH)。
  • 镜像消费方：总开关开启且超阈值仍无网络数据 → request(STATE_MISSING)。
  • 解码 / 未知类型异常捕获处 → request(UNKNOWN)。

要求

  1. 双向限流（客户端预检 + 服务端防刷），冷却先固定 100t。
  2. resync 幂等：仅重置客户端镜像来源的基线，不改服务端权威数据，不新增订阅。
  3. 触发保守：仅可判定异常；不得因“恰好无变化”触发。
  4. resync 响应总是附带重推 SyncConfigSyncPacket。
  5. 可选：debug 开关下记录 resync 原因用于定位。
  6. enabled=false 时不发 resync。

八、横切要求

性能

  • 空闲：0 回调、0 发包（仅 dirty 布尔短路）。
  • 变化：网络级差分一次 + O(订阅者) 发包；scope=ITEMS 时成本同现状。
  • 大 scope 仅在显式启用时产生带宽 / 内存开销。

兼容

  • 默认配置下所有现有功能行为不变。
  • PrimaryNetClientStorage 旧静态 API 保留。
  • 旧配置键不迁移。

线程

  • 镜像 / 会话仅主线程访问；BD delta 回调只置 volatile 脏位。

九、验收清单

  1. compileJava 通过。
  2. 登录即收配置包；重载配置客户端同步更新。
  3. 切 scope：服务端推送内容、客户端 supports、业务取数三者一致。
  4. enabled=false / ITEMS：与当前版本无差异（回归）。
  5. TACZ 合成库存：客户端重算结果与服务端请求通道一致（数量、NBT partial、桶装折算）。
  6. 人为制造 CONFIG_MISMATCH → 客户端自动请求并恢复一致；连续异常被双向限流。

十、风险与回滚

  • 高风险：阶段 2 / 3（BD Any 语义、清空路径、越界清理）；阶段 5b（聚合逻辑两端一致）。
  • 策略：每阶段独立提交、独立验证、可单独回滚；阶段 1 / 3a / 3b 为行为不变的纯新增 / 重构，可先行合入。
  • 最大风险点：JEI 同步依赖 Any 做全量重扫——Hub 扩展 / typeMask 改写若有误，会出现“清空 / 大量删除后客户端不刷新”的静默回归，需重点回归。
