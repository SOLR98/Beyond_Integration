# Beyond Integration 四分支现状分析（2026-11-20）

> **分析对象**：`D:\BI\worktrees` 下的 4 个 worktree
> **方法**：git 对象级比对（blob 哈希逐文件判同）、`diff --numstat` 量化、注解/API 计数、构建脚本静态检查
> **限制**：未执行 Gradle 构建——本机 `~/.gradle` 无依赖缓存，4 个 worktree 也都没有 `build/` 产物；因此"能否编译"只能静态判断，下文标注为"未验证"
> **基准提交**：`0.8F=dd3722a`、`0.8N=7e231fd`、`1.20.1F=f0c55b3`、`1.21.1N=966eab3`

## 0. 口径与结论

### 0.1 设计口径：按主模组版本分线，每条线再分加载器

仓库实际是按**主模组版本**分线的（BI 自身版本与所依赖的 BD 版本同步走）：0.8 线吃 BD 0.8.x 的 Compixel/BdPage 体系，0.7 线吃 BD 0.7.x 的旧 GUI 体系；每条线内部再按 MC/加载器分 1.20.1 Forge 与 1.21.1 NeoForge。`docs/35-version-matrix.html` 开头就是这个口径（"两条主线：BD 0.7.30 与 BD 0.8.x；每条线下分 1.20.1 与 1.21.1 —— 共 4 个工程"）。

| 主线 | 1.20.1 / Forge | 1.21.1 / NeoForge | 这一行代表什么 |
|---|---|---|---|
| **0.8 线** | `0.8-1.20.1-forge`（BI 0.8.2-fix-beta，BD 0.8.9） | `0.8-1.21.1-neoforge`（BI 0.8.1-beta，BD 0.8.9） | 同一产品 × 两个加载器 |
| **0.7 线** | `1.20.1-forge`（BI 0.7.3，BD 0.7.30） | `1.21.1-NEOFORGE`（BI 0.7.1-fix，BD 0.7.x） | 同一产品 × 两个加载器 |

因此真正"应该长得一样"的是**同一行的两支**；同一列只是"同一个加载器上的新旧两个产品"。下文两套口径都给：

- **分线口径**（设计/交接口径）：同一行的两支是否交付同一套功能 → §3.5；
- **代码口径**：逐字节重合度，看实现有没有真的收敛 → §3.1–§3.4。

结论先说：两者不一致——**分线按主模组版本分，代码却按加载器聚类**。分线做成了，跨加载器收敛没做成。

### 0.2 十一条结论

1. **四个分支不是一棵树，是两棵不相干的树**。`1.20.1F` 与 `1.21.1N` 有共同祖先 `8114e19`（2026-06-09）；两条 0.8 分支是**无父提交的孤儿导入**（`f321ffb` / `d7f9640`，2026-11-08），与 0.7 线、与彼此**都没有 merge-base**。这意味着 0.8 线无法 cherry-pick、无法三方合并，只能整树比对。
2. **分线口径与代码口径不一致**：设计上按主模组版本分 0.8 / 0.7 两条线、每条线再分两个加载器；但逐字节相同率显示，同线跨加载器的两对（`0.8F↔0.8N` **27%**、`1.20.1F↔1.21.1N` **20%**）**低于**跨线同加载器的两对（`0.8F↔1.20.1F` **74%**、`0.8N↔1.21.1N` **63%**）。
3. **同线对齐度：0.8 线反而比 0.7 线整齐**——0.8 线两支各自独有文件 8 / 18，功能域基本齐平；0.7 线 124 / 80，且 Neo 侧缺药水护符整套、经验棒与终端绑定明显偏薄（详见 §3.5）。这与"0.7 是正式线、0.8 是实验线"的旧说法相反。
4. **0.8 线是从同加载器的 0.7 分支派生、再适配 BD 0.8 的产物**：这解释了为什么同线两支反而不如各自与 0.7 亲戚像——沿用了加载器专属代码，没有做跨加载器收敛。
5. **四份拷贝没有公共模块**：四个分支合计 1574 个源文件（Java 1554 + Kotlin 20）、17.0 万行；其中 Java 按内容去重后有 1060 种不同实现，而**四个分支同路径且同内容的仅 42 个文件（占 4%）**——这 42 个才是真正可移植的内核。
6. **0.8 线的"实验/未完成"标签已经过期**：`0.8N` 有 404 个源文件、4.2 万行、80 个 Mixin 类（`mixins.json` 77 条），功能域覆盖 soul/mana/ammo/feeder/charm 全套，早就不是文档里说的"仅 GUI 骨架"。文档滞后比代码落后更危险。
7. **真正做跨版本兼容的地方只有 MixinPlugin**：4 份 `MixinPlugin` 分别 270/320/222/75 行，用 ModList、类资源探测、ASM 方法签名、包布局探测做运行时门控；但它们**一行日志都没有**，跳过即静默。
8. **两条 0.7 分支今天不能干净克隆构建**：`1.20.1F` 写死 `org.gradle.java.home=C:\Program Files\Java\jdk-17` 且依赖 `libs/jei-...jar`；`1.21.1N` 依赖 `libs/emi-...jar`，而 `libs/` 已被 .gitignore 且 worktree 中不存在。0.8 线反而更干净（已全部改 CurseForge 坐标）。
9. **0.8F 存在未提交的构建改造**：工作区里 `build.gradle` / `gradle.properties` / `settings.gradle` 三个文件被改（加阿里云镜像、删 `java.home`），**没有提交**。谁 clone 谁回到旧状态。
10. **`mixins.json` 策略四份四样**：`required` 只有 `1.21.1N` 是 `true`；`injectors.defaultRequire:0` 只有两条 N 分支有；`refmap` 只有两条 F 分支有。同一功能在不同分支的"注入失败"行为不一致。
11. **命令层是最大的重复与漂移源**：`NetworkInsertCommand` 四份分别是 1115 / 857 / 901 / 311 行，**功能已经不对等**（0.8F 有 TACZ 弹药/配件插入与药水护符分支，另三条没有）；命令层四条合计约 2.07 万行。

### 1.2 拓扑（关键结构事实）

```
1.20.1-forge      f0c55b3 ●──┐
                             ├── 共同祖先 8114e19（2026-06-09）
1.21.1-NEOFORGE   966eab3 ●──┘        分叉后各走 15 / 12 个提交
```

- 两条 0.8 分支的根提交信息都是"0.8.x 线导入：NEW_*"，即**把外部工程整树导入**，因此丢掉了全部历史。

- 0.8 线的提交粒度极粗：3–4 个提交承载 4 万行。

远端有 7 条相关分支（4 条主线 + `docs/planning-archive` + 2 条 `fix/*`），其中两条是"临时工作分支"，本地已把正式分支名指到了它们上面：

| 本地分支 | 实际指向 | 远端正式分支落后情况 |
|---|---|---|
| `0.8-1.20.1-forge` | `dd3722a` = `origin/docs/planning-archive` | `origin/0.8-1.20.1-forge` 还在 `9eecb71` |
| `0.8-1.21.1-neoforge` | `7e231fd` = `origin/fix/0.8.1-taczaddon-sentry-compat` | `origin/0.8-1.21.1-neoforge` 还在 `3d8e0ed` |

另有 `origin/fix/0.8.2-taczaddon-compat`（`04d4cac`，是本地 0.8F 的父提交）。**远端没有名为 `new` 的分支**，"NEW_*" 只是导入前的工程名（`settings.gradle: rootProject.name = 'new_forge_1-20-1'`）。

> 风险：别人按分支名拉到的是两周前的代码；`docs/planning-archive` 这种"文档分支"实际承载了 0.8F 的全部代码，语义完全错位。

### 3.5 同线对齐度（按"主模组版本"口径重算）

§3.1 的矩阵说明代码按加载器聚类；但按设计口径，**同一行的两支才是同一个产品**。把比较对象换成"同一行"后，两行的健康度差别很大：

| 指标 | 0.8 线（0.8F ↔ 0.8N） | 0.7 线（1.20.1F ↔ 1.21.1N） |
|---|---|---|
| 源文件 | 394 / 404 | 410 / 366 |
| 公共路径 / 相同 | 376 / 102（27%） | 286 / 57（20%） |
| 各自独有文件 | **8 / 18** | **124 / 80** |
| 变更量 | 17,772 行 | 36,844 行 |
| 构建脚本 | 都已改公开源（CF/Modrinth），无本地源码构建 | 都依赖仓库外 `libs/*.jar` |
| 结论 | 一对基本对齐的产品分支 | 一对已显著漂移，Neo 侧是滞后方 |

功能域层面的同线差异（数字为文件数，F 侧 / N 侧）：

| 功能域 | 0.8 线 | 0.7 线 | 读法 |
|---|---|---|---|
| 药水护符 | 10 / 10 | **10 / 0** | 0.7 线 Neo 完全没有 |
| 经验棒 | 18 / 19 | **14 / 6** | 0.7 线 Neo 明显薄 |
| 终端绑定 | 11 / 10 | **12 / 5** | 同上 |
| 磁铁 | 0 / 0 | 10 / 8 | 该功能只存在于 0.7 线 |
| 漏斗 | 0 / 0 | 5 / 5 | 同上 |
| 工作台/GUI | 33 / 34 | 64 / 67 | 0.7 线两支齐平，但都是自绘 GUI |
| 附魔台 | 22 / 23 | 15 / 20 | 0.8 线两侧都做了 Apoth 附魔台 |
| 女仆 TLM | 14 / 14 | 8 / 7 | 0.8 线两侧都含 P 点类（入口当前被注释掉） |
| TACZ | 27 / 29 | 24 / 20 | 0.8 线两侧更齐 |

两条推论：

1. **0.8 线的"同一产品两个加载器"基本兑现**——功能清单齐平，差异集中在适配细节（8 vs 18 个独有文件里，多数是 `ItemNbt`/`BdItemData` 这类垫片或 TUD/Thirst 这类单侧兼容）。
2. **0.7 线反而是分裂的那一对**——124 个 Forge 独有文件（自绘 GUI、磁铁、漏斗、RS 集成、工作台菜单）在 Neo 侧没有对应物；Neo 侧连药水护符整套都没有。文档把 0.7 叫"正式线"、0.8 叫"实验线"，与其实际对齐度是反的。

也就是说：**分线口径下该做的收敛，0.8 线做了一半（功能齐、代码没合），0.7 线基本没做（功能都不齐）。**

## 10. 建议（按性价比排序）

### P0 — 半天内可做完，直接消掉三条高风险

1. **提交 0.8F 的三个构建脚本改动**（阿里云镜像 + 删 `java.home`）。当前 HEAD 的 `java.home` 写死本机路径，等于把"能不能构建"绑在某一台机器上。
2. **修 1.20.1F**：删 `org.gradle.java.home`；`libs/jei-15.56.jar` 改 Modrinth 坐标（`maven.modrinth:jei:...`），与 0.8F 现在的做法一致。
3. **修 1.21.1N**：`libs/emi-*.jar`、`libs/sentrymechanicalarm-*.jar` 改公开坐标（0.8N 的 `0.8.x-TACZ与哨戒兼容记录.md` 里已给出 CF 坐标 `create-sentry-mechanical-arm-repairs-extensions-1791865:9624673`）；补 `.gitignore`，把 `build/` 移出索引。
4. **0.8 线补 `LICENSE`**（GPL-3.0 全文），与 `mods.toml` 声明一致。

### P1 — 一周内，消掉"静默失效"

5. **MixinPlugin 统一加日志**：抽一个 4 行工具方法，`shouldApplyMixin` 每次返回 `false` 时 `LOGGER.warn("[BI] skip mixin {} on {} (reason)")`。这是四条分支里性价比最高的改动——现在"功能没了"和"模组没装"在日志上完全无法区分。

### P2 — 一个月，做结构性收敛

8. **在 0.8 线内抽 `common`，而不是跨四条一起抽**：分线口径下，只有同一行的两支共享完整功能清单。以 §3.4 的 42 个四分支同内容文件为起点（它们同时也是 0.8 线两侧同内容），加上 `ChargePlatform`/`ItemNbt`/`BdItemData`/`EnchantRegistryCompat`/`PacketHandler` 这 5 个垫片，做成 `common` + `forge` + `neoforge` 三件套；0.7 线保持独立，不参与这次重构。
9. **命令层单独重写**：四条分支的命令层合计约 2.07 万行（单份 3.7k–6.3k），是重复度最高、价值最低的拷贝。建议每个主线只保留一份 `CommandTree`（Brigadier 结构 + `CommandLang` 文案），把"插入能力"做成按分支注册的 `InsertProvider`，让三种能力集变成配置而不是三份代码。
10. **给 0.7 线一个明确定性**：它现在 Neo 侧缺药水护符整套、经验棒和终端绑定只有 Forge 侧的一半、磁铁/漏斗/自绘工作台没有移植（§3.5）。要么把 Neo 侧补齐到同线齐平，要么公开声明"0.7 线仅维护 Forge、Neo 冻结"。**继续把它称作"正式线"、把 0.8 称作"实验线"，会让所有人都按错误的前提做取舍。**

### 不建议做的事

- ❌ 用 `git merge` 合并 0.8 双分支：无共同祖先，结果是整树冲突。
- ❌ 把两条 0.7 分支也并入上面的 `common`：0.7 与 0.8 的包结构（`handler/init` vs `feature`）已经不同，先做 0.8 内部收敛，再谈跨主线。
- ❌ 在未构建验证的情况下发布 0.8F 的 `0.8.2-fix-beta`：工作区构建脚本改动未提交，产物不可复现。
